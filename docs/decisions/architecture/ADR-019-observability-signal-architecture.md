# ADR-019: アプリケーションのObservabilityシグナル設計

- Status: Accepted
- Date: 2026-09-25
- Owners: Human project owner
- Related requirements: FR-007, NFR-001, NFR-002, NFR-004, NFR-005
- Supersedes: none
- Superseded by: none

## Context

NFR-005は、仕組みの導入後、失敗したリクエストとバックグラウンド処理を診断できる運用シグナルを求める。現在の実装はGoの`net/http` API、ReactのブラウザUI、PostgreSQL、OIDCで構成される。APIには起動失敗時の限定的な`log`出力があるが、リクエスト単位の構造化ログ、メトリクス、トレースの共通規約はない。バックグラウンド処理、デプロイ先、通知方式は未決定である。

FR-007のAudit Eventは、誰がいつ申請・承認操作をしたかを説明する永続的な業務記録であり、ADR-004によりトランザクション内の追記として扱う。運用ログやトレースは欠落・サンプリング・保存期間の変更があり得るため、Audit Eventを代替しない。OIDC token、session cookie、PKCE verifier、申請本文などの機微情報を診断情報へ流さない設計が必要である（ADR-005、ADR-011）。

このADRはアプリケーションが生成する信号の方式と境界を決める。具体的な監視サービス、ログ・メトリクス・トレースの保存先、保存期間、アラート閾値、SLO、デプロイ形態は決めない。外部転送を有効にする前に、選定した運用環境とデータ保護要件を別途レビューする。

## Decision drivers

- 失敗したHTTPリクエストを、秘密情報を出さずにリクエスト単位で追跡できること
- 将来のバックグラウンド処理でも、同じ相関・失敗分類を使えること
- ADR-004のAudit Eventと診断信号の責務を混同しないこと
- 高カーディナリティのラベルや過剰なログによる費用・漏えいリスクを抑えること
- 特定の監視ベンダーへアプリケーションコードを結合せず、依存関係と運用負荷を抑えること
- `net/http`とGo/TypeScriptの現行構成で検証可能であること

## Options considered

### Option A: Go標準ライブラリの構造化ログのみ

Goの`log/slog`でJSONログを標準出力へ出し、リクエストID、経路、結果、所要時間を記録する。集計・検索は実行環境のログ機能へ任せる。

**利点**

- Goアプリケーションの新しい本番依存関係が不要
- 現行の単一APIでは、失敗リクエストの調査を小さく始められる
- 導入とローカル検証が単純

**欠点**

- 遅延や失敗率の時系列監視にログの後処理が必要
- 将来の処理間の因果関係を標準的なトレースとして追えない
- 大量ログを診断用に保持すると費用と機微情報の管理負担が増える

### Option B: 構造化ログとOpenTelemetryのメトリクス・トレース

Goの`log/slog`でJSONログを標準出力へ出す。HTTPと将来のジョブ境界にOpenTelemetryのメトリクス・トレースを計装し、環境で有効化した場合にOTLPでCollector等の受信先へ送る。相関IDと、記録されたトレースのtrace IDをログに含める。保存先はアプリケーションコードに埋め込まない。

**利点**

- ログで個別の失敗を、メトリクスで発生傾向を、トレースで処理の経路を調べられる
- OTLPの受信先を変更しても、業務コードの計装を維持しやすい
- 非同期処理が導入された際に同じ文脈伝播方式を拡張できる

**欠点**

- OpenTelemetryのSDK・exporterと受信先の設定、更新、終了時flushが必要
- シグナルの収集量、ラベル、サンプリングを誤ると費用や情報漏えいにつながる
- Collectorと保存先を運用する段階では追加の基盤判断が必要

### Option C: 特定の監視サービスのSDKへ直接計装

サービス固有のSDKでログ、メトリクス、トレースを送信し、そのサービスの画面とアラートを使用する。

**利点**

- 一つのサービスで収集、検索、可視化をまとめられる場合がある
- サービス固有の機能を直接利用できる

**欠点**

- 未決定のデプロイ先や監視サービスをこの段階で固定する
- SDK、認証情報、課金、データ所在地、退出手順の評価が必要
- サービス移行時に計装コードの変更が広がる可能性がある

## Decision

**Option Bを採用する。** 実装では、次のアプリケーション側の規約を採用する。

1. Go APIは`log/slog`のJSON形式で標準出力に構造化ログを出す。各HTTPリクエストの終了時に、生成または検証済みの相関ID、HTTP method、ルートテンプレート、status、所要時間、失敗分類を記録する。認証・認可失敗も診断対象とするが、機微な入力値は記録しない。クライアントから渡された相関IDを使う場合は形式・長さを検証し、不正値は新しく生成する。
2. OpenTelemetryでHTTPサーバーのリクエスト件数・所要時間・失敗を測るメトリクスとトレースを計装する。ラベルにはルートテンプレート、method、statusなど上限が管理できる値だけを使い、URLの実ID、Member/Organization ID、任意のエラー文を入れない。詳細トレースはサンプリング可能とし、件数・失敗率を把握するメトリクスはサンプリングに依存させない。
3. export先と認証情報は環境設定で与え、OTLP受信先を有効にした環境で送信する。Collectorまたは保存先の製品をこのADRで確定しない。export障害が業務リクエストの成否を変えないようにし、収集失敗を運用者が把握できるようにする。
4. 将来バックグラウンド処理を導入する際は、ジョブ種別、実行結果、所要時間、再試行と失敗を同じ規約で記録し、受け渡し可能な相関文脈を伝播する。ただし、キュー、broker、再試行方式はその導入時のDecisionで決める。
5. Audit EventはADR-004の永続的な業務記録として維持する。観測信号にはtoken、cookie、authorization header、接続文字列、PKCE関連値、申請本文を含めない。主体や申請の追跡が必要な場合も、必要性とアクセス制御を別途評価するまで識別子をログ・属性へ加えない。

ブラウザ側のRUM、セッション再生、監視サービス、ダッシュボード、アラート、保持期間は対象外とする。これらは運用環境とデータ保護の条件が明らかになった時点で判断する。

## Rationale

Option Aは追加依存を抑えるが、NFR-005が求める将来のバックグラウンド処理を含む診断では、時系列の傾向と処理経路をログから再構成する負担が残る。Option Cは運用先未決定の現段階でロックインを生む。Option Bは追加のSDKと運用設定を必要とする一方、個別失敗、傾向、処理経路の役割を分けられ、保存先の選定を後続判断に残せる。Go標準の`log/slog`を使い、OpenTelemetryのGo SDKでは成熟しているメトリクス・トレースに範囲を限定する。現時点のOpenTelemetry GoのログSDKは成熟度が異なるため、ログの生成は標準ライブラリに留める（[Go SDKの状態](https://opentelemetry.io/docs/languages/go/)、[Goの構造化ログ](https://pkg.go.dev/log/slog)）。

## Consequences

### Positive

- HTTP失敗を相関ID、結果、所要時間から調査する共通規約ができる
- 失敗率と遅延の傾向を、個別ログの量を増やさず把握できる
- 運用先の選定とアプリケーション側の計装を分離できる
- Audit Eventの証跡性を診断信号の収集状態に依存させない

### Negative / trade-offs

- Goの本番依存関係と、SDK・exporterの保守が増える
- 収集先、認証、ネットワーク、保持、費用、アクセス制御は別途決定・運用が必要
- 相関ID、サンプリング、失敗分類、ラベル上限の規約を継続してレビューする必要がある

## Validation

- `httptest`で成功、4xx、5xx、panic相当の失敗を発生させ、リクエストごとの相関ID、ルートテンプレート、status、所要時間、失敗分類を確認する。存在しないルートや認証経路も対象にする。
- テスト用のメモリ内exporterまたは同等の受信先で、HTTP件数・所要時間とトレースの相関、ラベルの上限を確認する。export停止時もAPI結果が変わらないことを確認する。
- token、cookie、authorization header、接続文字列、申請本文がログ・span属性・metric属性に現れないことを、代表的な認証失敗と業務操作で確認する。
- Audit Eventの既存テストを維持し、ログやexportの失敗によって監査追記・状態遷移が変わらないことを確認する。
- 非同期処理を導入する際は、ジョブの失敗、再試行、文脈伝播をその処理方式のテストで追加検証する。

## Revisit conditions

- 実測した信号量・費用・性能影響が運用上の上限を超える場合
- デプロイ先とデータ保持・アクセス制御の要件が決まり、Collectorまたは保存先の選定が必要になった場合
- 非同期処理や複数サービス間の呼び出しを導入し、文脈伝播の契約を確定する場合
- OpenTelemetry GoのログSDKの成熟度が変わり、`slog`との連携が保守上有利になった場合
